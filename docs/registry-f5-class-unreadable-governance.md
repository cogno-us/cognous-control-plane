# Registry F5 per-class `on_unreadable` (`GovernedClassUnreadableWorkflow`)

Status: BUILDER_TESTED developer documentation. Non-authorizing. Not independently qualified. Module: `agent_control_plane.registry_f5_class_unreadable_governance`. Governing documents: Static Migration Plan v1.1 (adoption merge `6f600ab1150f00ef3d96834159b1807e866a78b6`), Engineering Plan v1.5, adopted inventory audit (Registry PR #60), Engineering Constitution `1c2e920f4e58e07a52e8e2408a506cf7dbc1292b` (`ADOPTION.md` read at the same revision). Registry contract: `r08-v5` (`docs/r08-v5-contract.md` in cogno-us/cognous-ocs-registry PR #64).

## What it does
A Registry `r08-v5` selection (`class_on_unreadable`: class id to `refuse` | `bounded_tolerance`) can only move a host `ActionClass.on_unreadable` from `bounded_tolerance` to `refuse`. The workflow verifies the selection with Registry (`verify_and_decide_v5`, required participation, exact `Ed25519Verifier`), builds ONE effective `RuntimeAuthorityProfile` and passes it to the unchanged `BoundedAuthorizationWorkflow`. The effective value per class is the stricter of host and Registry. A looser Registry value changes nothing; a Registry class the host does not define refuses; a host class the record does not name keeps the host value (the scoped action's class must be named).

## What the value governs (and does not)
`on_unreadable` is read in exactly two places in `bounded.py` (pinned by a test): the invalid-class rule (an irreversible class whose value is not `refuse` is `action_class_invalid`) and `_read_grant` (a cached positive may replace an unreadable grant status only for a non-irreversible `bounded_tolerance` class). A Registry `refuse` therefore removes the cached-grant tolerance. It does NOT disable the cached-purpose-snapshot path (reversibility/0.1 `judge_cached_purpose`), which never reads the value; wiring it would need a protected-evaluator change and is not made here.

## Host validity first (irreversibility)
A host class that is irreversible AND `bounded_tolerance` is an invalid host declaration under the existing evaluator (`bounded.py:2111`, `action_class_invalid`: every action of the class refuses). The ORIGINAL host profile is validated against that invariant BEFORE any selection source is read or Registry is called (`host_class_defect`; construction refusal `host_class_invalid`). The Registry may only reduce permissions in an already admissible host profile; it must not repair an invalid declaration or conceal a host defect, whatever value the record carries (`refuse` or `bounded_tolerance`), in the on_unreadable-only and the joint workflow. The unmodified workflow still holds such a class with `action_class_invalid` (tested as the oracle). A valid irreversible class is already `refuse`; no Registry value changes it. `registry_would_heal_invalid_class` stays inside `derive_unreadable` as defence in depth for direct callers (tested).

## Commitment and approvals
`approval_commitment(profile, context)` already hashes `profile.model_dump()`, so the effective value is bound before approval issuance. A selection that narrows nothing yields a byte-identical profile and existing approvals stay valid; a narrowing changes the commitment and an old approval holds with `runtime_authority_approval_mismatch`; a new approval over `workflow.runtime_authority_profile` (the EFFECTIVE profile) is required. Nothing is rewritten. The persisted decision binding's `catalogue_digest` equals the effective-profile digest. Only one field of each class changes; every other class property and profile member is byte-identical (tested).

## Lifecycle
Every governing selection is verified at construction, at the start of `decide`, at the start of `execute`, and at the commit gate immediately before `destination.apply` (the destination is wrapped; four source calls per effect). Each must reproduce the bound identity and the held profile is re-checked against the bound digest at each boundary (before and after the source calls). Refusals before the gate raise `RegistryClassUnreadableRefused` (a `PermissionError`) before any state write; at the gate the existing `DefinitiveDestinationRejection("registry_f5_unreadable_selection_invalid")` is raised, the destination is not called and the attempt is recorded `failed`, which blocks automatic retry. Residual window: the gate runs immediately before `destination.apply` is entered, not inside the destination's transaction (accepted for bounded engineering only). Selection-source custody, rollback and epoch duties are the host's (`registry-f4-selection-source-custody.md` applies unchanged); there is no Control Plane ratchet and no new destination interface.

## Composition with the Registry class status age (optional, one workflow)
Constructing the workflow with `class_age_scope` and `class_age_selection_source` adds the M12 class-age selection to the SAME workflow. The age component is derived by the unchanged `derive_effective`; the unreadable value is composed over the age-effective profile. The bound identity is the tuple (age effective map, Registry age digest, age-profile digest, unreadable effective map, Registry digest, FINAL profile digest). Both sources are verified at every boundary; either failing, being revoked or withdrawn, or changing any member refuses. There is no fallback to either family alone, and the pair must share consumer, tenant and action (operation ids may differ). The age pair is all-or-nothing. Without it the age field is untouched. Using the two families as separate overlays is not supported (a second workflow around the first would not bind the other family's identity).

## Scope and refusals
One (consumer, tenant, action) scope per workflow. Refusal codes are listed in the module header; every refusal is `non_authorizing`. A profile carrying `policy_binding` is refused. Excluded and untouched: `requires_revocation_assurance`, reversibility, `anchor_deadline_to_inputs`, terminal revocation, `ObservationPolicy`, `identity_max_age_seconds`, `mandate_max_age_seconds`, constructor `clock_tolerance_seconds`, F4 scalars.

## Tests and CI
`tests/test_f5_class_unreadable_governance.py` (148 tests; real synthetic Ed25519, no test doubles for the Registry verdict) needs a Registry checkout at the exact `PIN` containing `r08-v5`. With `OCS_REQUIRE_REGISTRY_PIN=1` a missing/wrong pin or missing PyNaCl is a failure; otherwise the module is reported NOT RUN. CI runs it in a dedicated step with a second Registry checkout and a junit gate (no skips, no failures, at least 148 tests). If the Registry PR head changes, `PIN` here and the CI ref must be updated together.
